## 1. Физический движок: cannon-es → ?

### Текущее состояние

Проект использует **cannon-es** (форк Cannon.js с ES-модулями). Реализована кастомная аркадная модель автомобиля через `semi-authoritative velocity override`:

- Кузов — `Box` с смещённым COM (`shapeOffsetY`)
- `applyForce` + ручная коррекция заноса (`lateral *= (1 - grip * surfaceGrip)`)
- Sensor-тела (`collisionResponse = false`) для триггеров
- Hover-шасси: ручная позиция по Y (`body.position.y = surfaceY + rideHeight`)

**Известные проблемы cannon-es:**
- Медленный (чистый JS, без WASM)
- Нет встроенных trigger'ов — приходится эмулировать через `collisionResponse = false`
- `Cylinder` ориентирован вдоль оси Y (ограничения для подвески)
- Проект на «жизненной поддержке» (pmndrs/cannon-es только чинит критические баги)
- SAPBroadphase — медленнее AABBTree при большом количестве тел
- Нет Continuous Collision Detection (CCD) — пролет сквозь объекты на высоких скоростях

### Варианты замены

#### 1.1 Rapier (WebAssembly) ⭐ Рекомендовано

| Критерий | Оценка |
|----------|--------|
| Производительность | **9/10** — Rust/WASM, в 5-10x быстрее cannon-es |
| Фичи | **9/10** — CCD, built-in triggers, joints, коллизии, сенсоры |
| Документация | **9/10** — одна из лучших в индустрии |
| Размер бандла | 150-250 KB WASM (сжимается до ~60 KB gzip) |
| Типизация | Отличная (Rust → TypeScript bindings) |
| Сообщество | Растущее (используется в Bevy, Redpanda, Godot 4) |
| Кривая обучения | Средняя (новый API, но хорошая документация) |

**Преимущества:**
- **Производительность:** WASM-реализация на Rust. Для сцены с 4 машинами + 200 снарядов + 500 тел трассы — стабильные 60 FPS на слабых устройствах
- **Built-in Trigger Mode:** `ColliderDesc::trigger(true)` — не нужно эмулировать через `collisionResponse = false`
- **CCD (Continuous Collision Detection):** Защита от пролёта сквозь объекты на высоких скоростях (актуально для ракет и скоростных поворотов)
- **Stable joints:** Spring-damper, distance, revolute — можно постепенно реализовать более реалистичную подвеску
- **Parallel physics step:** Многоядерная симуляция (на десктопе)
- **Определённость:** Детерминированная симуляция (важно для netcode)

**Недостатки:**
- WASM-бандл ~200 KB (cannon-es ~40 KB)
- Новый API — потребуется переписать `PhysicsWorld` и всю интеграцию с ECS
- Нет `RaycastVehicle` (как и в cannon-es) — аркадная модель остаётся той же
- На мобильных Safari WASM может быть чуть медленнее из-за ограничений

**Оценка перехода:**

| Параметр | Оценка |
|----------|--------|
| Сложность миграции | Средняя-Высокая (1-2 спринта, ~2-3 недели) |
| Выигрыш в производительности | Высокий (2-5x для сложных сцен) |
| Выигрыш в стабильности | Высокий (CCD, triggers, лучше solver) |
| Риск | Средний (новый API, нужно тестировать на Safari) |
| **Рекомендация** | **ПЕРЕХОДИТЬ** (фаза 10+) |

**Рекомендуемый план миграции:**
1. Спайк (2-3 дня): прототип `RapierWorld` с одной машиной
2. Сравнительное тестирование: cannon-es vs Rapier (FPS, кол-во тел, стабильность)
3. Поэтапная замена: `PhysicsWorld` → `RapierPhysicsWorld` (такой же API)
4. Замена `Box`/`Plane`/`SAPBroadphase` на аналог Rapier
5. Замена sensor-тел на `ColliderDesc::trigger(true)`
6. Добавление CCD для снарядов (`ColliderDesc::set_ccd(true)`)

#### 1.2 Ammo.js (Bullet → WASM)

| Критерий | Оценка |
|----------|--------|
| Производительность | 7/10 — WASM, но тяжелый JS bridge |

| Размер бандла | 1-2 MB WASM |

**Вердикт:** Слишком тяжёлый. RaycastVehicle в нашем проекте не нужен (аркадная модель). **Не рекомендовано.**

#### 1.3 OimoPhysics

| Критерий | Оценка |
|----------|--------|
| Производительность | 6/10 |
| Фичи | 5/10 — базовый набор |
| Размер бандла | 60 KB |
| Активность | Низкая |

**Вердикт:** Легче cannon-es, но не стоит усилий. **Не рекомендовано.**

## 2. Графический движок: ogl → ?

### Текущее состояние

Проект использует **ogl** — минималистичный WebGL2-рендерер (~12 KB):

- Базовые примитивы (Box, Cylinder, Sphere, Plane)
- Lit-материалы через custom shader
- Instanced particles (3000 max)
- Camera, frustum culling
- **Нет:** post-processing, shadows, glTF loader, decals, PBR, bloom

**Известные ограничения:**
- Пост-обработка (vignette, color grading) — вручную через render-to-texture
- glTF-загрузчика нет — нужны примитивы или кастомный парсер
- Decals (следы заноса) — эмулируются плоскими mesh-лентами
- Нет теней из коробки
- Нет PBR-материалов (только базовый lit)

### Варианты замены

#### 2.1 Оставить ogl ⭐ Рекомендовано для MVP

| Критерий | Оценка |
|----------|--------|
| Размер | **12 KB** — невероятно лёгкий |
| Контроль | **10/10** — полный контроль над шейдерами |
| Гибкость | **9/10** — ничего лишнего |
| Производительность | **9/10** — минимум оверхеда |
| Для нашей игры | **9/10** — аркадные гонки не требуют сложного рендера |

**Преимущества ogl:**
- Идеален для аркадных гонок: простая геометрия, яркие цвета, частицы
- Минимальный оверхед — на 4 машины + трассаogl быстрее трёх.js в 2-3x
- Полный контроль над шейдерами (можно добавить кастомный PBR, rim-light, rust shader)
- Нет абстракций, которые мешают в нашем case
- Размер бандла ~12 KB (three.js ~600 KB, Babylon.js ~500 KB)

**Недостатки:**
- Нужно писать всё вручную (shadow maps, post-processing, glTF)
- Нет сообщества и готовых примеров
- Время разработки визуалов выше

**Вердикт:** Для текущего scope (MVP, аркадные гонки, 4 машины, примитивная геометрия) **ogl — оптимальный выбор**. Переход на трёх.js добавит ~600 KB бандла и 1-2 недели разработки ради фич, которые мы не используем.

## 3. NavMesh: нужна или нет?

### Что такое NavMesh

NavMesh (Navigation Mesh) — это полигональная сетка, покрывающая проходимые области уровня. ИИ использует A*/JPS для поиска пути по этой сетке.

### Анализ для нашей игры

#### ЗА (почему может понадобиться)

1. **Динамические препятствия:** Если в будущем появятся перекрываемые участки трассы (разрушаемые мосты, завалы) — NavMesh можно перестроить
2. **Сокращения углов:** ИИ может находить более короткие пути через «разрывы» трассы (трамплины, обрывы)
3. **Универсальность:** Если проект вырастет до open-world — NavMesh будет необходим

#### ПРОТИВ (почему НЕ нужна)

1. **Трасса — это сплайн, а не свободное пространство.** ИИ следует по precomputed waypoints и racing line. Нет «свободного» пространства для навигации.
2. **4 машины, 6 трасс.** A* по сплайну — O(n) на waypoint. NavMesh — O(n log n) на построение + O(k log k) на поиск. Сплайн быстрее.
3. **Curvature уже предвычислен.** Формула `v_target = min(maxSpeed * skill, sqrt(grip * 9.82 / curvature))` — это и есть «идеальная скорость» на повороте. NavMesh не даёт ничего нового.
4. **Racing line уже реализован.** `wp.racingLine = wp.position + right * offset` — это и есть оптимизированная траектория.
5. **Доп. зависимость:** navmesh-generator ~100 KB, навигация по сплайну — 0 KB.
6. **Сложность:** NavMesh для криволинейной трассы с обрывами и трамплинами — нетривиальная задача. Как покрывать обрывы? Как делать «мосты»?

#### Сравнение подходов

| Критерий | Сплайн (текущий) | NavMesh |
|----------|-----------------|---------|
| Сложность реализации | ✅ Реализован | Средняя (построение + A*) |
| Производительность | ✅ O(n) на waypoint | O(n log n) |
| Размер бандла | ✅ 0 KB | ~100 KB |
| Динамические препятствия | ❌ Нет | ✅ Да |
| Оптимизация траектории | ✅ Racing line | ✅ Shortcuts |
| Интеграция с curvature | ✅ Готово | Нет (нужно дописывать) |

### Вердикт

**NavMesh НЕ нужен для текущей и ближайшей версии игры.**

Трасса — это заранее определённый сплайн с предвычисленной curvature и racing line. Нет свободного пространства, для которого NavMesh имеет смысл. Если в будущем появятся динамические разрушения трассы — можно рассмотреть, но это маловероятно.

**Рекомендация:** ❌ **Не добавлять.** Остаться на сплайновой навигации.

## 4. RVO: нужна или нет?

### Что такое RVO

RVO (Reciprocal Velocity Obstacles) — алгоритм децентрализованного избежания столкновений для множества агентов. Каждый агент рассчитывает оптимальную скорость, чтобы не столкнуться с другими.

**Библиотеки:**
- `rvo2-js` (порт C# RVO2) — alpha, ~15 KB
- `navgo-rvo` — ~20 KB

### Анализ для нашей игры

#### ЗА

1. **Обгоны:** Машины могут обгонять друг друга без жёсткой колонны
2. **Естественное поведение:** Плавное распределение по ширине трассы без «залипания»
3. **Масштабируемость:** RVO хорошо работает при 10+ агентах (у нас 4)

#### ПРОТИВ

1. **4 машины — слишком мало.** RVO раскрывается при 10-50+ агентах. Для 4 машин — избыточен.
2. **Скорость важнее обгонов.** В аркадных гонках приоритет — скорость, а не элегантность обгонов. ИИ уже уклоняется через `EVADING` (racing line offset ±2м, JumpJets).
3. **Конфликт с физикой.** RVO рассчитывает «идеальную скорость», но мы используем `semi-authoritative velocity override`. RVO будет конфликтовать с нашей моделью управления.
4. **ИИ уже уклоняется.** Состояние `EVADING` в XState уже реализует обход препятствий (racing line offset, JumpJets).
5. **Доп. зависимость и сложность.** RVO требует регулярных обновлений позиций всех агентов (каждый кадр), что добавляет оверхед.
6. **TDR (Time-Distance-Rate) уже в EVADING.** Формула `v_target = sqrt(grip * 9.82 / curvature)` уже учитывает траекторию.

#### Сравнение

| Критерий | Без RVO (текущий) | С RVO |
|----------|------------------|-------|
| Сложность | ✅ Реализован | Средняя |
| Размер бандла | ✅ 0 KB | ~15-20 KB |
| Обгоны | ❌ Ручные (EVADING) | ✅ Автоматические |
| Интеграция с физикой | ✅ Нет конфликтов | ⚠️ Конфликт с velocity override |
| 4 машины | ✅ Достаточно | ❌ Избыточен |
| 10+ машин | ⚠️ Будет проблема | ✅ Хорошо масштабируется |

### Вердикт

**RVO НЕ нужен для текущей версии игры.**

Для 4 машин текущая система `EVADING` (racing line offset ±2м + JumpJets) покрывает все сценарии обгона. RVO раскрывается при 10+ агентах и требует изменения архитектуры (переход от velocity override к position-based control).

**Рекомендация:** ❌ **Не добавлять сейчас.** Добавить только если:
- Количество ИИ увеличится до 10+
- Будет реализован мультиплеер (8+ машин одновременно)
- Будет переход на position-based AI control

## 5. ИИ: State Machine → Utility AI / GOAP / Behavior Tree?

### Текущее состояние

**XState v5 State Machine** (4 состояния):

```
cruising → attacking → evading → recovering → cruising
```

- `cruising`: следование по racing line, `v_target = sqrt(grip * 9.82 / curvature)`
- `attacking`: raycast → стрельба (конус 35°, дальность 45 м)
- `evading`: препятствие вперёд → offset ±2м / JumpJets; угроза сзади → мина
- `recovering`: застревание / падение → респаун

**Плюсы текущего подхода:**
- Простой, понятный, отлаженный
- XState v5 — строгая типизация, guards, actions
- Легко отлаживать (видим текущее состояние)
- 84 строки кода

**Минусы:**
- Жёсткие переходы (event-driven) — нет плавных градиентов
- Сложно добавить новые поведения (каждое новое действие = новое состояние или guard)
- Нет приоритизации (что делать: атаковать или уклоняться?)

### Сравнение подходов

#### 5.1 Utility AI ⭐ Рекомендовано для масштабирования

**Суть:** Каждому действию присваивается «utility score» (полезность). Действие с максимальным score выполняется.

**Пример для нашей игры:**

| Действие | Факторы | Score |
|----------|---------|-------|
| CRUISE |_curvature, fuel, position | 0.8 |
| ATTACK | enemy_in_cone, distance, ammo | 0.9 |
| EVADE | obstacle_distance, boost_ammo | 0.6 |
| BOOST | straight_road > 200m, nitro_ammo | 0.7 |

```typescript
// Псевдокод
const scores = {
  cruise: 1.0 - curvature * 2.0,
  attack: enemyInCone ? (1.0 / (1.0 + distance)) * aggression : 0,
  evade: obstacleInFront ? (1.0 / (1.0 + obstacleDistance)) : 0,
  boost: straightRoadLength > 200 && nitroAmmo > 0 ? 0.8 : 0,
};
const bestAction = argmax(scores);
```

**Плюсы:**
- **Плавные переходы:** Нет резких switch — score градиентный
- **Приоритизация:** `attack` (0.9) > `boost` (0.8) — автоматический выбор
- **Легко добавлять действия:** Новое действие = новая функция score
- **Тонкая настройка:** Веса легко балансировать (aggression, skill)
- **Хорошо для гонок:** Скорость + атака + уклонение — всё одновременно

**Минусы:**
- Нужно определить функции score для каждого действия
- Может быть «непредсказуемым» (score может резко меняться)
- Нет явной последовательности действий (не видит «план»)

**Оценка перехода:**

| Параметр | Оценка |
|----------|--------|
| Сложность | Средняя (нужно переписать AIState → UtilityEvaluator) |
| Выигрыш в качестве ИИ | Высокий (более естественное поведение) |
| Выигрыш в балансе | Высокий (weights = баланс) |
| Риск | Низкий (score функции можно тестировать отдельно) |
| Рекомендация | **ПЕРЕХОДИТЬ (фаза 10+)** |

#### 5.2 Behavior Tree (BT)

**Суть:** Дерево узлов (Sequence, Selector, Condition, Action). Похоже на FSM, но иерархично и переиспользуемо.

**Пример:**

```
Selector
├── Sequence [Recover]
│   ├── Condition: stuck > 3s
│   └── Action: respawn
├── Sequence [Evade]
│   ├── Condition: obstacle_in_front < 15m
│   └── Action: jump / offset
├── Sequence [Attack]
│   ├── Condition: enemy_in_cone
│   └── Action: shoot
└── Sequence [Cruise]
    └── Action: follow_racing_line
```

**Плюсы:**
- **Масштабируемость:** Дерево можно комбинировать (поведенческие блоки переиспользуются)
- **Приоритизация:** Selector автоматически выбирает первый успешный узел
- **Читаемость:** Структура дерева интуитивно понятна
- **Стандарт индустрии:** Unreal Engine, Assassin's Creed, Gears of War
- **Декомпозиция:** Сложное поведение = комбинация простых узлов

**Минусы:**
- **Сложнее FSM:** Нужно понимать tree-логику (Sequence, Selector, Decorators)
- **Отладка:** Tree traversal сложнее чем FSM state transition
- **Overhead:** Tree evaluation каждый кадр
- **Для 4 состояний:** FSM достаточно — BT добавляет абстракцию без реальной пользы

**Оценка перехода:**

| Параметр | Оценка |
|----------|--------|
| Сложность | Средняя-Высокая (новая парадигма, новая библиотека) |
| Выигрыш в качестве ИИ | Средний (лучшая структура, но не обязательно лучше поведение) |
| Выигрыш в масштабируемости | Высокий (переиспользование узлов) |
| Риск | Средний (новая парадигма, нужно переучиваться) |
| Рекомендация | **Оставить FSM (для 4 состояний BT — избыточен)** |

---

#### 5.3 GOAP (Goal-Oriented Action Planning)

**Суть:** ИИ определяет цель (goal) и строит план действий для её достижения. Похож на STRIPS-планировщик из классического ИИ.

**Пример:**

```
Цель: "Enemy is close and has low HP"
Доступные действия: [Approach, Shoot, Evade, Boost]
План: [Approach(enemy), Shoot(enemy)]
```

**Плюсы:**
- **Естественное поведение:** ИИ «думает» о целях, а не о состояниях
- **Гибкость:** Одно и то же действие может служить разным целям
- **Для RPG/Sims:** Идеально для игр с открытым миром и множеством NPC

**Минусы:**
- **Слишком сложно для гонок:** В гонке нет «целей» в смысле GOAP — есть «ехать быстрее»
- **Планирование каждый кадр:** Дорого для JS/WASM
- **Малая польза:** 4 состояния FSM уже покрывают все сценарии
- **Over-engineering:** GOAP создан для игр вроде F.E.A.R. (сотни NPC, открытый мир)

**Оценка перехода:**

| Параметр | Оценка |
|----------|--------|
| Сложность | Высокая (планировщик, world state, action definitions) |
| Выигрыш в качестве ИИ | Низкий (для гонок не нужно «планировать цели») |
| Выигрыш в масштабируемости | Средний |
| Риск | Высокий (over-engineering, мало пользы) |
| Рекомендация | ❌ **НЕ переходить** |

### Итоговая рекомендация по ИИ

| Фаза | Рекомендация |
|------|-------------|
| MVP (сейчас) | **Оставить FSM (XState v5)** — 4 состояния, 84 строки, работает |
| F10+ (масштабирование) | **Рассмотреть Utility AI** — если нужно тонкая настройка поведения ботов |
| F10+ (структура) | **Behavior Tree** — если нужно переиспользование поведенческих блоков |
| Любая фаза | **GOAP — НЕ использовать** |

**Почему FSM достаточно сейчас:**
1. 4 состояния покрывают все сценарии (cruising, attacking, evading, recovering)
2. Guards в XState v5 уже обеспечивают условные переходы
3. 84 строки кода — минимальный оверхед
4. Легко отлаживать и балансировать (aggressionLevel, skill, reactionTime)
5. Переход на Utility AI даст заметный выигрыш только при 10+ ботах и/или сложной балансировке
