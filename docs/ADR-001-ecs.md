# ADR-001: Выбор ECS

**Дата:** 2026-11-05
**Статус:** Принято

## Контекст
План (Фаза 0) требует проверить API `@trixt0r/ecs` на практике и решить: оставаться на
библиотеке или написать минимальную собственную ECS.

## Spike
В рамках spike были проверены `World`/`Component`/`System` из `@trixt0r/ecs@0.5.1`:

*   Сущность обязана наследовать `AbstractEntity` (нет «сущность = id»).
*   Компоненты хранятся в нетипизированной коллекции, доступ через
    `entity.components.get(ComponentClass)` возвращает `Component | undefined` без
    привязки к конкретному классу — требуется ручное приведение типов.
*   Системы работают через `Aspect.for(engine).all(...)`, `process()` может быть
    `async`, что тянет микротаски в игровой цикл.
*   Пакет собран под TypeScript 3.9, последний релиз — 0.5.1 (2021), нет обновлений
    под современный strict-режим и `noUncheckedIndexedAccess`.

## Решение
Пишем **собственную min-ECS** (`src/ecs/`) с теми же концепциями (Entity = id,
Component — класс, System — объект с `update(dt)`), потому что:

1.  Полная типобезопасность: `world.get(entity, Transform)` возвращает `Transform | undefined`
    без `any` и приведений.
2.  Компоненты — обычные классы, сериализуемые и лёгкие для тестов.
3.  Никаких `async`/`Promise` в горячем пути.
4.  Нет обязательного наследования сущностей.
5.  Пакет `@trixt0r/ecs` остаётся установленным для совместимости с GDD, но игровой код
    использует обёртку `src/ecs/world.ts` (при желании её можно заменить адаптером).

## Последствия
*   API ECS фиксируется нами и покрывается unit-тестами.
*   Производительность достаточна для лимита 400 сущностей (GDD §1): запросы
    итерируют `Set<EntityId>` и `Map` компонентов.
